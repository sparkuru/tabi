# 通用清单技术设计

## 1. 边界与数据流

`JSON 文件/粘贴 → 服务端校验与预览 → 整体导入草稿 → 管理员发布 → 用户直接完成/添加记录 → 历史与分享`。

沿用 React Web、FastAPI、Pydantic、SQLAlchemy/PostgreSQL 与现有媒体存储。通用导入使用独立契约与持久化身份记录，既有 OCR 转录复核入口和种子命令继续兼容。通用内容复用现有清单、条目、外链及同清单关联模型，不增加按主题分支的业务表。

## 2. v1 文件契约

```json
{
  "format": "tabi.checklist",
  "version": 1,
  "key": "python-basics",
  "list": {"title": "Python 基础", "category": "学习"},
  "items": [
    {
      "key": "functions",
      "name": "函数",
      "description": "编写一个带参数和返回值的函数。",
      "links": [{"title": "学习资料", "url": "https://example.com/functions"}]
    }
  ]
}
```

| 位置 | 必填 | 可选与规则 |
| --- | --- | --- |
| 顶层 | `format`, `version`, `key`, `list`, `items` | `source`；一份文件一张清单 |
| `list` | `title` | `summary`, `category`, `sort_order`，沿用清单内容限制 |
| `items[]` | `key`, `name` | 现有条目内容字段、外链以及 `related_keys`；不接受数据库 ID、媒体 key 或发布状态 |
| 身份 | 清单 key 和每个条目 key | 小写字母/数字开头，后续可包含 `._-`，最长 80 字符；清单 key 在通用导入中全局唯一，条目 key 在该文件内唯一 |
| 地点 | 无 | 使用既有 `none/physical/area/online` 契约；坐标成对并注明坐标系 |
| 来源 | 无 | 条目 `source` 优先，否则使用顶层来源；实际核实时间仅在有真实依据时填写 |
| 顺序 | 无 | 未提供条目 `sort_order` 时按数组顺序；规范化时生成最终排序值 |
| 同清单关联 | 无 | `related_keys` 引用本文件条目，拒绝未知目标、自关联和重复引用 |

条目内容字段包括 `summary`, `description`, `category`, `tags`, `suggested_action`, `recommendation`, `reference_note`, `reference_as_of`, `missing_fields`, `sort_order`、地点字段、`source`, `verified_at`, `links`。名称 trim 后不能为空。拒绝未知字段、未知版本与错误类型；规范化后的名称/地址继续遵守现有同清单查重规则，重复时指出两个条目位置。JSON Schema 表达单字段约束，跨条目关联和规范化查重由服务端补充校验。

首版上限为一张清单 200 个条目、UTF-8 JSON 2 MiB；保留现有文本、链接、标签上限。文件/粘贴共用相同服务端解析，输入大小在解码前限制。未知版本不会按 v1 猜测解释。导入文件不包含用户记录、完成状态或图片；管理员可在导入后维护封面。

实施检查补齐存储边界：导入排序值为有符号 32 位整数；URL 原值及规范化后均须不超过 2048 字符，名称/地址组合经原查重算法规范化后须不超过 512 字符。超限返回对应字段的 `422`，不是数据库错误；这是现有存储约束的补充校验，不改变既有维护接口或用户数据。

交付文档为 `docs/checklist-format.md`、由后端契约生成的 `docs/checklist.schema.json` 和 `backend/data/examples/` 下的最小、待办、学习及少量真实 OCR 来源示例。OCR 示例选择现有资料中的少量记录，使用独立的示例 key 和准确来源；不自动把旧 172 条重新导入一份。旧完整种子文件继续用于原有初始化命令。

## 3. 导入 API 与持久化

建议接口：

- `POST /api/admin/checklist-imports/preview`：验证同一份文件载荷，不写入清单或审计。有效输入返回标题、条目预览、数量、`ready/existing/conflict` 及现有清单 ID；语法/字段错误返回可定位的 `422`，体积超限返回 `413`。
- `POST /api/admin/checklist-imports`：再次独立校验，整体写入草稿。首次 `201`；同身份同摘要 `200` 并返回既有清单/条目 ID；内容不同 `409`，无覆盖行为。

两条接口验证管理员身份与 CSRF。预览结果不是后续写入的授权或可信输入，写入时重新检查身份、规范化与冲突。前端输入变化后使旧预览失效。网络失败保留输入，成功后跳转或选择导入清单。

新增 `checklist_imports` 表：`id`, `package_key`（唯一）, `format_version`, `payload_hash`, `list_id`, `item_ids_by_key`（JSON 映射）, `imported_by`, `imported_at`。数据库 ID 仍由服务端生成；文件 key 不用作公开数据库 ID。该表表示导入身份和创建事件，不伪造 OCR 复核批次，也不存用户记录。

摘要使用经过校验、展开默认值、生成有效顺序和继承来源后的完整有效载荷，按固定对象 key 排序进行 UTF-8 JSON 序列化后取 SHA-256。对象字段顺序与空白不影响摘要，数组顺序和有效内容变化会影响摘要。比较的是初次导入内容摘要，不用管理员当前编辑内容重算摘要，因此原文件重试不会还原编辑或重新发布。

清单、条目、外链、关联、导入身份与操作审计在同一数据库事务写入。先在内存完成跨条目检查，再写入。`package_key` 唯一约束处理并发竞争；冲突事务整体回滚，重新读胜出的身份记录并按摘要返回复用结果或 `409`。拒绝跨清单关联。不同 key 允许同名清单，条目同名同址在不同清单仍各自独立。

## 4. 发布与管理状态

增加显式批量接口 `POST /api/admin/lists/{list_id}/publish-all`：一次事务发布清单及 `draft` 条目，已发布条目保持状态，`unpublished` 条目跳过。没有任何可发布或已发布条目时拒绝发布，防止产生空的公开清单。操作返回实际发布/跳过数量并写审计。

保留旧逐条维护及旧单层发布接口语义；管理页默认操作改用批量发布，并显示“发布清单及 N 个草稿条目”。用户显式重新发布一张下架清单时仍跳过已下架条目。批量操作不修改来源与核实时间，不宣称导入即已核实。OCR 警告继续被既有编辑保护。

管理员响应新增独立的状态数量，不把公开 API 的 `item_count` 改成包含草稿的数量。管理列表/详情可看到总数、草稿、已发布和已下架数；公开目录继续只返回双方都发布的内容。导入预览直接显示文件中的草稿内容，访问控制在服务端执行。

## 5. 完成记录

无内容记录是有效的完成记录，使用现有 `Checkin` 表；不增加独立完成状态或主题专用逻辑。调整创建/编辑记录以及删除最后一张照片的非空限制，确保所有入口采用同一规则。

新增 `POST /api/items/{item_id}/complete` 作为“直接完成”入口：验证登录、CSRF 和公开状态；首次创建无正文/照片、当前记录时间、`private` 的记录。使用现有用户级 `Idempotency-Key` 与操作指纹防止网络重试。若该用户已有有效记录，返回已有记录，完成操作不再追加；用户主动“添加记录”仍使用原接口并允许多次记录。

PostgreSQL 中完成操作锁定目标条目行，在锁内检查已有记录并创建，串行化对同一条目的并发完成请求；幂等键唯一约束仍是数据库保障。已有记录的返回属于无写入操作，不改变该记录的正文、可见性或时间。创建记录的幂等键被其他操作使用时仍冲突。

UI 在未完成条目提供“标记完成”，已完成时显示状态；“添加记录”独立可用。请求期间禁用重复点击并保留重试键，成功刷新清单、条目与历史缓存。游客通过登录后继续。删除单次记录的能力用于撤销那次完成，删除最后一条有效记录才恢复未完成；不使用取消勾选批量删除有内容的历史。

纯完成记录在历史、详情和显式公开分享中显示“已完成”及条目、时间等实际信息，不假称有照片。照片和心得可后续补充或清空。分享继续显式选择公开，隐私撤销、删除、管理员隐藏及原图权限照旧生效。

## 6. 页面与文案

- 首页使用“清单”标题和实际卡片列表；删除大段宣传 hero、英文装饰副标题和页脚口号。
- 条目详情只在实际存在内容时显示详情、地点、建议、外链等区域；无地点不显示占位句。
- 统一使用“记录”“添加记录”“记录时间”“进度”，移除对到店/出游的默认假设。真正的用户心得、管理员内容和 OCR 原始推荐文字不做自动改写。
- 必要的来源、隐私、错误、下架状态提示保持简短且可读；OCR 未核实提示可简化，但不能消除来源与事实状态。
- 沿用现有 React Web/Lucide/颜色基础。按钮至少 44px，可键盘操作；错误有字段路径与修正方式，使用 `role=alert`/关联描述；异步操作显示忙碌、成功和失败。细化依据见 `research/format-and-import.md`，不采用与项目不符的 newsletter 模板或原生 App 技术建议。

## 7. 兼容、风险和回滚

- 新导入表为加法迁移，不重写既有清单/条目/记录。旧 OCR 种子命令、稳定 ID、真实来源提示和复核导入接口保留，旧客户端的有内容记录继续正常工作。
- 现有 spec 中“至少文字或照片”的规则会在实施后更新；隐私、幂等、去重和历史不变量继续有效。生成 OpenAPI 与 HeyAPI 客户端，不手改生成文件。
- 并发复用、事务回滚与完成行锁需在 PostgreSQL 验证；仅 SQLite 测试不能证明 PostgreSQL 约束与行锁。
- 在隔离数据库/媒体目录和受控测试账号验证。降级代码前，先处理新产生的无内容记录兼容性；不得删除用户记录来满足旧版本的非空假设。迁移回滚只在测试库演练，真实库保留新表并采用向前修复或关闭新入口。
- 没有外部发布动作；本任务提供可运行代码和验证结果，具体实例的数据导入与发布由有权限的操作者明确执行。

## 8. 实际 preview 同步验收补充

2026-10-04 用户要求补齐实际 preview 账号并沿用户使用的 HTTP 地址验证。增加独立 Playwright preview 配置，复用当前锁定版本和 Chromium 双视口，测试目录与隔离写入套件分开。`TABI_PREVIEW_BASE_URL` 必填且不默认回退 dev 地址；`TABI_PREVIEW_CREDENTIALS_FILE` 指向包含 email/password 的本地凭据 JSON，不将凭据写入源码、命令参数、报告或 Git。

检查范围为实际网页登录、管理员身份/管理页、合法 JSON 的不写入预览，以及登录退出。使用真实 Cookie/CSRF 和 HTTP 响应，不 mock API；不导入、发布或清理既有数据。该检查证明同一用户入口可验收，不替代已有 PostgreSQL 并发/事务与完整业务套件。所有样例、写入测试继续遵守获授权的数据范围。
